# PR #179: September 14 follow-up

This report verifies the 21 findings posted on [PR #179](https://github.com/manifest-network/manifest-ledger/pull/179#issuecomment-5668018655) and [ENG-859](https://linear.app/liftedinit/issue/ENG-859/enforce-hard-timeout-and-tenant-active-cap-gates-when-acknowledging). Both contained the same review of `6b02665ecc75b14b6bd548075da39651cd8b928f`.

Confidence scores express confidence in the finding and its stated scope. They are not probabilities that the code has no remaining vulnerabilities. Nineteen findings resulted in implementation, test, documentation, or live-control changes. Two retain previously documented tradeoffs rather than introducing another consensus mechanism or deleting reproducibility evidence.

## Measured limits and compatibility

A 2,000-period account with 2,000 distinct denominations occupied about 84 KB but previously cost approximately one second and 498 MB per locked-balance calculation. The SDK fix measured approximately 1.9 ms and 1.5 MB on the same shape. Differential fuzzing completed 21,934 executions in 15 seconds; all vesting packages pass, including a real 2,000-denomination account-creation test. Checked integer addition, validation order, canonical results, boundary shortcuts, and nil/empty behavior are covered against the prior algorithm.

The SDK patch changes no public signatures, protobufs, stored account layout, module version, KV accesses, or explicit gas charges. Existing vesting accounts need no migration for this patch alone. It is nevertheless consensus-sensitive: an undiscovered arithmetic or time-boundary regression could change locked balances and transaction acceptance. Differential tests reduce that risk but do not prove equivalence for every state. Rehearse representative existing schedules and bank sends against the parent and patched SDK, comparing balances, transaction results, charged gas, and committed state. Deploy it with the coordinated Ledger upgrade; the broader Ledger migration and finite-query-gas configuration changes are separate requirements.

No official equivalent was found on September 14 in v0.50.15, v0.53.8, v0.55.0, or the inspected 0.50/0.53/main branch heads (99% confidence for those sources). The [v0.50.15 vesting code](https://github.com/cosmos/cosmos-sdk/blob/8c7741050ad8c7ef0b6afd9129fb2dd9a91d30d4/x/auth/vesting/types/vesting_account.go#L297) and [current upstream coin addition](https://github.com/cosmos/cosmos-sdk/blob/8f265eb5186b1ec9243e588549b5aa8676418493/types/coin.go#L334) still repeat growing-total aggregation. [Upstream PR #25860](https://github.com/cosmos/cosmos-sdk/pull/25860) was closed as stale without merging; its proposed faster individual merge would still repeatedly copy growing prefixes. Keep this vesting-only fork commit isolated and replace it when an official equivalent passes the same compatibility and workload checks. Upgrading the SDK solely for this issue does not currently remove the defect. Upstream acceptance and long-term maintenance remain open; no upstream submission was made by this review.

A near-budget 39,000-denomination account still occupied about 1.64 MB and used roughly 120 ms/29 MB in the concurrent local run. These measurements are examples, not universal CPU/memory ceilings. Query gas does not replace gateway concurrency/rate limits and production-capacity rehearsal.

CreditEstimate allocation measurements fell approximately 14–21% across the reviewed worst-case shapes. Concurrent builds made timing comparisons noisy, so no latency-improvement claim is made. Metered query tests show that 100 leases with 100 items each succeed, while 300 such leases and a 2.25 MB periodic account exhaust the default budget. The SDK maps these panics to ABCI ErrPanic/native-gRPC Internal; the explicit lease/item/balance ceilings retain their documented ResourceExhausted errors. Native gRPC carries cancellation into the handler; the pinned SDK's ABCI query entrypoint discards transport cancellation.

Existing node configurations must set a positive top-level `query-gas-limit` before the coordinated restart. Init/testnet defaults and generated config comments reflect the new policy; the upgrade test stages the positive value in the old binary's configuration. This is independent of the Wasm-specific query budget.

The maintainer explicitly selected self-approval for this single-maintainer project. Independent CODEOWNER approval is therefore advisory until another maintainer joins. This does not protect against a compromised administrator, who can edit the server controls. The read-only release-control preflight uses an administrator's `gh` session; it is not presented as an automatic workflow check using an underprivileged GITHUB_TOKEN.
