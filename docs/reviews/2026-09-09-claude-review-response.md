## Confirmed accounting and lifecycle findings

| Finding | Disposition and evidence | Confidence |
| --- | --- | --- |
| F02: total balance includes vesting locks | **Fixed; high severity.** An attacker can pre-create a vesting account at an unused derived credit address. Billing previously counted its locked coins toward credit, while bank sends could not spend them. A real SDK permanent-lock message plus funding reproduced `spendable balance 7200umfx is smaller than 7201umfx` with a read-only Go overlay restoring the old total-balance accounting. Admission, settlement, queries, invariants, migration and import now use per-denomination `max(0, total - locked)` at block time. Locks are read once per account/batch; unrelated bank denominations are not scanned for settlement. Real delayed, periodic, continuous and permanent vesting fixtures cover this behavior. | 100% |
| F02: every transfer fails / ACTIVE forever / no recovery | **Overstated.** The same original implementation closes successfully after enough unlocked funding covers accrued charges. Only settlement that exceeds spendable funds fails. This does not reduce the need to fix the accounting mismatch. | 100% |
| F01: relax backing checks or clamp arbitrary terminal shortfalls | **Not adopted.** The issuer-debit vector was already closed. The new vesting fix corrects admission/backing inputs; dropping the backing invariant or indiscriminately clamping does not specify who bears a shortfall among sibling guarantees. Preserve the existing strict reservation contract. An arbitrary corrupt-state repair mechanism would require a separately specified allocation policy. | 99% |
| F07: non-CLOSED `closed_at` accepted | **Fixed; medium.** Import and current-state validation reject `closed_at` except on CLOSED leases. Settlement and estimates select the close timestamp only for CLOSED state. Real PENDING/REJECTED/EXPIRED flows and malformed-state probes confirm that unprovided service cannot become billable through this field. | 100% |
| F12: failed expiry consumes successful-expiration quota | **Fixed; medium.** EndBlock continues through bounded candidate pages using an exclusive composite-key cursor local to the block. It closes each iterator before mutations, counts successful expirations only, and retries failures next block. A fixture with 101 persistent failures followed by 105 healthy expired leases makes exactly 100 healthy expirations, then five next block; an all-failure pass terminates without partial lease changes. | 100% |
| F23: unbounded stored rejection/closure reasons | **Fixed.** Genesis/current-state validation applies the same 256-byte bound as message validation. | 100% |

The F02 fix does not reject funding merely because the address has a vesting account: that would let pre-creation disable funding. Deriving/querying an address remains read-only. Already-v4 reservations must remain fully spendable-backed; this is not a repair mechanism for arbitrary current-state corruption. The supported, not-yet-deployed v2→v3→v4 cutover retains its allocation/expiration policy with corrected spendable inputs. No tokenfactory fork or additional state format is required.

The offline preflight now requires decoded auth state and `--at <RFC3339>` rather than valuing vesting from an export's original `genesis_time`. Schema 5 separately reports total `bank_balance`, `spendable_balance`, `planner_time`, and `input_genesis_time`. Sequential migration and legacy InitGenesis parity tests cover locked-backed PENDING expiration and ACTIVE allocation. An independent check also found SDK panics on malformed auth-account envelopes; these are converted to input errors at the narrow offline boundary, with regression fixtures. Consensus code does not recover from arbitrary panics.

## Validation and remaining limits

Final commands/results are recorded in the accompanying [feedback validation](2026-09-09-claude-review-validation/README.md). Baseline bug assertions are kept separate from desired-behavior tests. Confidence does not claim no vulnerabilities remain. The final suite measures
76.9% statement coverage across both modules excluding generated files (billing
79.9%, SKU 66.9%; keepers 84.7%/85.6%). CLI coverage is lower at billing 51.9% and
SKU 30.4%, so generated-transaction/error matrices remain a specific follow-up.
This default package coverage profile does not include cross-package execution
of dependency code or merge the separate simulation/race/fuzz campaigns.

The two failed CI jobs on `0307b4b` were independently inspected: Build Manifest failed reading a sum.golang.org tile for Consul SDK, and arm64 E2E image build failed downloading tokenfactory from proxy.golang.org; both reported HTTP/2 INTERNAL_ERROR from the peer. These are external download failures, not passing build evidence. The new PR head must run its own CI.

Outstanding deployment gates remain: production-sized migration/query/invariant timing and cardinality (ENG-890), broader behavioral/fuzz infrastructure (ENG-869), domain ownership verification (deferred ENG-62), real provider/wallet authentication-v2 rollout (ENG-925), simulator phase/time-queue limitations (ENG-914/ENG-915), and consumer/client compatibility. No live-chain policy audit, release deployment, or proof of complete vulnerability absence is claimed. Billing v3 is not deployed; arbitrary direct-v3 upgrade semantics are outside the supported migration path.
